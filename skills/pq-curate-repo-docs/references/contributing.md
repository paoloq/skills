# Contributor guide

CONTRIBUTING walks a contributor, human or agent, from idea to merge; GitHub links it whenever someone opens an issue or pull request.

## The path

1. Keep it as `CONTRIBUTING.md` at the repository root; when a docs site holds the full guide, keep a short root file that links it.
2. Say what needs agreement before any code: a feature or design change starts in an issue or discussion, while a bug fix or trivial change goes straight to a pull request.
3. Then cover the path in the order a contributor meets it: development setup, the checks to run before submitting, opening the pull request, and how review and merge work.
4. Own the development commands: setup, tests, linters, formatters, and the gate.
5. Point to the pull request template for the per-change checklist rather than repeating it.

## Policies

6. When the project has an AI-use policy, state its core rules in a short section and link the policy file.
7. When a SECURITY.md exists, send vulnerability reports through it, never to issues or pull requests; when a code of conduct exists, link it.

## Shape

8. Write each step as one action with its conditions, in numbered order where order matters.
