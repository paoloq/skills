# READMEs

A README is the project's front door: what the project is, how to start using it, and where to go next.

## Root README

1. Open with the project's name and one line on what it is and who it is for.
2. Give install and a first run as copyable commands in fenced blocks; when a docs site owns installation, give one prominent link there instead.
3. Link the docs site or docs folder for everything deeper, such as API reference, configuration, guides, and architecture.
4. Link the contributing guide, and say where to get help.
5. State the license.

## Style

A README is read by people deciding whether to use the project, so it should look inviting and scan at a glance.

6. Open with a logo or banner, with light and dark variants when one would vanish on the other background.
7. Follow it with one row of badges that report real status, such as CI, version, license, downloads, or chat.
8. Show the product when it is visual or claims speed: a screenshot, a short animation, or a benchmark chart.
9. Near the top, list the highlights or the reasons to use it in a few short bullets.
10. Put the single notice that matters most in a callout such as `> [!NOTE]` or `> [!TIP]`.
11. Keep images in the repository, link them relatively, and give each one alt text.

## Package READMEs

12. Give each separately published package a README on one template shared across the repository: its name, a one-line purpose, install, a docs link, and where to get help. An internal component gets none; its rules belong in a nested AGENTS.md.
